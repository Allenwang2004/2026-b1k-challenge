# BEHAVIOR-1K 2026 Challenge — Status and Plan to Submission

**Date:** 2026-09-29 · **Submission deadline:** 2026-10-16 (17 days)

---

## 1. Summary

We replaced the stage-conditioning signal in the baseline policy with one derived from
BDDL goal literals. On the task we have studied most, the resulting policy reaches
**q = 0.667 and a 40% success rate over the 10 public instances** — well above the level
of the current public leaderboard (best entry: q = 0.3221, success rate 0.148).

More importantly, the change fixed a *correctness* defect rather than a tuning one: the
previous target was a quantity that cannot be computed at inference time at all. That
argument holds independently of any score.

We have since isolated exactly why performance still collapses on long-horizon tasks, and
the diagnosis is specific and actionable. This document proposes the next change, and
sets out the schedule.

**The binding constraint on this project is not research — it is rollout compute.** A full
100-task submission needs roughly 886 GPU-hours of simulation. That is 37 days on one
machine, against a 17-day deadline. Section 6 addresses this directly; it is the single
decision that determines whether we submit a complete result.

## 2. What we changed, and why it is a correctness fix

The baseline policy is conditioned on a "subtask stage" — an integer telling the action
expert which phase of the task it is currently executing. The model both consumes this
number and predicts it.

**The original definition of that number:**

```
subtask_state = floor(num_stages × current_step / episode_length)
```

This is a fixed fraction of the way through the episode. It requires `episode_length` —
the *total* length of the episode.

That quantity does not exist while the robot is acting. It is known only in the offline
dataset, after the fact. At inference the data source is absent and the expression
returns 0. So the head was trained to regress a target that is, by construction,
undefined at test time. Whatever it learned to predict, it was not the thing it was
supervised on.

**Our replacement:**

```
subtask_state = number of BDDL goal literals currently satisfied
```

BDDL is the benchmark's own symbolic task definition. Each task states its goal as a
conjunction of literals — "the carrot is inside the bowl", "the cabinet is closed" — and
the simulator already evaluates them, because that is how the benchmark computes its
score. The count of satisfied literals is a function of the observable world state, so it
is defined at every instant, in training and at inference alike.

This is the whole of the change, and it is why we regard the direction as sound
regardless of the current numbers: we moved from an unlearnable target to a grounded one.

A useful consequence we discovered while validating this: the benchmark's own `q_score`
is exactly the fraction of satisfied literals. For a 14-stage task,
`q_score × 13` returns the final stage as an exact integer, every time. **Every rollout we
have ever run is therefore labelled ground truth for the stage predictor**, which lets us
evaluate stage-prediction changes offline, without spending simulation time. This is the
main reason we can now iterate quickly.

## 3. Results to date

### Task `picking_up_trash` (4 BDDL stages), 10 public instances

| Configuration | q_score | Success rate |
|---|---|---|
| Ours — BDDL conditioning | **0.667** | 0.40 |
| Ours — BDDL + terminal-stage clamp | **0.733** | 0.40 |
| 2026 public leaderboard, best entry | 0.322 | 0.148 |

The leaderboard figure is an average over all 100 tasks and ours is a single task, so this
is not a like-for-like comparison. It is reported to establish scale, not superiority.

Training diagnostics: stage accuracy 0.996, action loss 0.086.

### Task `sorting_vegetables` (14 BDDL stages), 10 public instances

Retrained with an identical recipe, changing only the task and its label file.

| | `picking_up_trash` | `sorting_vegetables` |
|---|---|---|
| BDDL stages | 4 | 14 |
| Stage accuracy (training) | 0.996 | 0.986 |
| Action loss | 0.086 | 0.184 |
| **Rollout q_score** | **0.667** | **0.354** |
| Success rate | 0.40 | 0.00 |

Training metrics are near-identical; rollout performance differs by roughly a factor of
two. **Training accuracy has no predictive power for rollout performance here.** That
observation drives everything in Section 4.

### Two things we must disclose

**(a) Against the baseline, the measured difference is zero.** The `sorting_vegetables`
comparison is now complete — both models, all ten public instances, paired:

| | Baseline checkpoint | Ours (BDDL) | Difference |
|---|---|---|---|
| Mean q_score (n = 10) | 0.331 | 0.354 | +0.023 |

Exact paired permutation test over all 1,024 sign assignments: **p = 0.85**. Wilcoxon
signed-rank: p = 0.69. Six instances favour ours, four favour the baseline. The 95%
confidence interval on the difference is [−0.154, +0.185] and contains zero.

**There is no measurable improvement on this task.** We report it as a null result.

On `picking_up_trash` we hold only two baseline instances, and on those two the two models
tie exactly (0.833 each). So we have no task on which superiority over the baseline has
been demonstrated.

**(b) The evaluation harness is substantially non-deterministic.** We ran the *same
checkpoint* on the *same instances* twice:

| Instance | Run 1 | Run 2 | Difference |
|---|---|---|---|
| 301 | q = 0.692 (stage 9/13) | q = 0.385 (stage 5/13) | −0.308 |
| 302 | q = 0.231 (stage 3/13) | q = 0.000 (stage 0/13) | −0.231 |

Same model, same instance, same normalization assets, same episode cap. **The run-to-run
spread on a single instance is larger than any model difference we have been trying to
measure.** We believe the main contributor is that the policy's random number generator is
not reset at episode boundaries, so an episode's outcome depends on how many episodes
preceded it; simulator physics contributes the rest.

This is a measurement defect, not a result, and it is fixable — but until it is fixed, no
single-run A/B at n = 10 should be believed. It is the first item in the plan.

**(c) The two findings above are connected, and they invalidate our measurement method.**
The model difference we measured (+0.023) is 9% of the run-to-run spread of a single
model (±0.27). Detecting an effect that size at this noise level, with 80% power, would
require roughly 1,200 instances — about 49 days of continuous single-machine rollout for
one task.

End-of-episode rollout scores are therefore the wrong instrument for guiding development.
We will not be able to tell good changes from bad ones this way, at any schedule we can
afford. The `q_score × N` ground truth described in §2 is the replacement: it yields 893
labelled stage decisions per episode instead of one number, which is roughly three orders
of magnitude more signal from the same simulation time. All model selection from this
point on should run against it, with rollouts reserved for final confirmation.

## 4. What is still broken, precisely

On `sorting_vegetables` the policy is asked "which stage are you in?" every 0.67 s, which
is 893 times per episode. Using `q_score × 13` as exact ground truth across the 10
episodes:

**The predictor's output changes 38× more often than the thing it is measuring.**

```
Times the true stage changes, per episode      4.6
Times the model's answer changes, per episode  178
```

Downstream, a voting tracker converts these votes into the stage that is fed back to the
action expert. It promotes on 2 of 3 votes and can skip two stages at once; it demotes
only on 3 of 3 votes and only by one. Any rapidly fluctuating input therefore ratchets
upward. Measured result: **the tracker overestimates the final stage by +3.9 on average**,
and 57% of all votes are provably above the stage the episode ever reached.

The consequence is not cosmetic. When the tracker reports stage 12 and the true stage is
4, the action expert is told it has already sorted twelve items and should begin the
thirteenth — while the robot has not yet picked up the first. It then executes behaviour
unrelated to the scene in front of it.

We tested every obvious repair. None works:

| Approach | Best result (mean absolute error vs. truth) |
|---|---|
| Raw prediction | 6.00 |
| Median-smoothed over 15–400 predictions | 4.50 – 5.20 |
| 16 different voting-tracker settings | 3.40 |
| **Ignore the camera; always output the constant 4** | **2.00** |

**Every readout of the current stage predictor is worse than a constant that never looks
at the image.** Confidence does not help either: predictions that are provably wrong carry
essentially the same margin as the rest (4.50 vs 5.25), so they cannot be filtered out.

### Why it fails

We checked the training labels across all 200 demonstrations per task. The stage sequence
is essentially monotone (1–2 episodes out of 200 contain a single decrement), and **every
demonstration runs to completion.**

So in the training distribution the stage always advances, and any feature that correlates
with elapsed time scores well — 0.986, as observed. **The answer "nothing has happened" is
absent from the training signal entirely.** The model was never asked to produce it.

At rollout the robot stalls for ten minutes in a scene unlike anything in training. The
model has no "no progress" response available, so it selects among fourteen unfamiliar
options — confidently — and the ratchet accumulates the noise.

## 5. The proposed change

Two modifications, addressing the cause rather than the symptom.

### 5.1 Give the model two points in time

Currently the model sees only the present frame. The BDDL labels are sampled every 30
simulator steps and held, so a stage label arrives 0–1 s after the event that caused it.
By the labelled frame, the action is over: a single image shows a finished state, never a
transition. A transition is not observable from one frame, so no amount of training can
teach it from one frame.

We add the three camera views from **40 frames earlier** (1.33 s, exactly two inference
intervals) alongside the current three. Change is then directly visible as the difference
between two observations.

- **Memory, measured:** 74.89 GiB → 80.55 GiB. It fits; no pooling or downsampling needed.
- **Inference cost:** none. The policy is already called every 20 steps, so the observation
  from two calls ago *is* the frame at t−40. We cache it; the simulator interface is untouched.
- **Position:** history views are appended after the current ones, so the existing three
  cameras keep their token positions and the pretrained layout is preserved.

### 5.2 Change the question

Replace the 14-way "which stage are you in?" with a binary question:

> **"Did a BDDL literal change during the last 1.33 s?"**

Across the same 200 demonstrations, **96% of the answers are "no"** (13 transitions × 40
frames out of ~12,400 frames). The model is now trained, on the overwhelming majority of
its examples, to say that nothing has happened. That is precisely the response missing
today, and it is missing for a structural reason: the old objective has no such class.

This also makes the second time point necessary rather than merely available — the question
cannot be answered from a single frame.

The stage number is then recovered by counting, which is valid because the labels are
monotone and each transition is +1:

```
stage = number of detected events so far
```

with two safeguards: count only the rising edge (the 40-frame window overlaps consecutive
queries, so one event produces two consecutive "yes" answers), and apply a refractory
period afterwards. Real stages last 861 frames on average — 43 inference intervals — so a
refractory of 10–15 intervals misses nothing real while bounding the maximum rate of
advance. Unlike the voting tracker, this has a physical ceiling on how fast it can climb.

### 5.3 Keep the old head

The existing 14-way head is retained and trained, at a cost of 30,735 parameters
(0.0009% of the model). It is not used to drive conditioning. It is kept because it is
nearly free, because an auxiliary objective is generally helpful, and above all because
logging both heads during a rollout gives a direct comparison against `q_score × N`
ground truth. **One training run then tells us which formulation is better, with no
guesswork.** If the new head does not win, that is also a conclusive answer.

## 6. Schedule, and the compute problem

### The constraint

Assume training occupies one instance of the current machine and rollouts run on a
separate machine, so the two proceed in parallel.

Rollout cost, computed from the benchmark's own per-task episode caps at our measured
throughput of 202 ms per simulated step:

```
100 tasks × 10 public instances = 15,818,280 simulated steps
  1 rollout machine   886 hours   36.9 days
  2 rollout machines              18.5 days
  4 rollout machines               9.2 days
```

Against 17 days remaining. Tasks range from 1.8 h (`turning_on_radio`) to 21.9 h
(`assembling_gift_baskets`) for their ten instances.

This is a worst case in that successful episodes end early — but our current success rate
is 0.40 at best and 0.00 on long tasks, so nearly every episode runs to timeout and the
worst case is close to the expected case.

**A complete 100-task submission cannot be produced from one rollout machine before the
deadline.** Three to four rollout machines are required, and they must run essentially
without interruption from roughly 6 October. Incomplete submissions are not partially
credited: the scorer divides by the expected task count, so an unrun task scores zero.

Securing that capacity is the decision that determines the outcome of this project, and it
should be made this week rather than after the model work concludes.

### Proposed timeline

| Dates | Work | Machine |
|---|---|---|
| **Sep 29 – Oct 1** | Implement history input, event target, event head, counting tracker. Fix per-episode RNG reset. Fix the evaluator so one crashed instance no longer aborts the remaining nine. | Dev |
| **Oct 1 – Oct 2** | Training run 1 — `picking_up_trash` (~16 h, estimated from 10.5 h at present cost) | Train |
| **Oct 2 – Oct 3** | Rollout run 1, two seeds, to measure against the variance established in §3(b). Training run 2 — `sorting_vegetables` (~14 h) begins concurrently. | Rollout / Train |
| **Oct 3** | **Decision gate.** Compare both heads offline against `q_score × N`. Criterion: the event head must beat the constant baseline (MAE < 2.00), which the current head does not. | — |
| **Oct 3 – Oct 6** | If the gate passes: train the submission model. If it fails: freeze the existing BDDL checkpoint and proceed to evaluation with it. | Train |
| **Oct 6 – Oct 14** | **Full 100-task rollout.** Must be parallel across 3–4 machines. | Rollout ×N |
| **Oct 14 – Oct 16** | Assemble submission, re-run failed instances, buffer. | — |

Two properties of this schedule are deliberate. The model is frozen on 6 October whatever
its state, because the evaluation block cannot be compressed. And the 3 October gate has a
pre-declared quantitative criterion, so the decision to continue or to fall back is not
made under deadline pressure.

### If only one rollout machine is available

Then a complete submission is not reachable and the objective should change now, not on
14 October. The defensible alternative is to submit a strong result on a declared subset
of tasks and report it as such. This should be decided this week.

## 7. Risks

| Risk | Assessment |
|---|---|
| **Rollout capacity** | The dominant risk. One machine gives 37 days of work against a 17-day deadline. Everything else is secondary. |
| **The event head may fail out-of-distribution too** | Possible. What we can guarantee is structural: its training objective contains the answer "no" in 96% of examples, and the current objective contains it in none. That is a difference in kind, not degree. The 3 October gate is designed to detect failure early. |
| **Step time increases** | Doubling the image tokens is estimated at +50% per step, which has not been measured. Memory is confirmed to fit. If training proves too slow, the history views can be pooled — measured at +5.04 GiB versus +5.66 GiB, with negligible difference, so this is a time trade-off only. |
| **Evaluation variance** | Established at ±0.3 q on a single instance for an identical model. Until the RNG fix lands, no conclusion should rest on a single 10-instance run. Two seeds are budgeted for the gate. |
| **Simulator crashes** | One instance diverged into a NaN quaternion and aborted the entire task with exit code 0 — losing eight instances and appearing to have succeeded. During a multi-day full-benchmark run this failure mode is severe. The fix is scheduled before evaluation begins. |

## 8. What we are asking for

1. **Rollout capacity for 3–4 machines from 6 October to 14 October.** This determines
   whether a complete submission exists.
2. **Agreement to the 3 October decision gate** and its criterion, so that the fallback to
   the existing checkpoint is a planned outcome rather than a failure.
3. **Continuation of the BDDL direction.** It corrected a target that could not be computed
   at inference; it produced 0.667 q-score and 40% success on the task we have studied,
   against 0.322 and 0.148 on the current public leaderboard; and it yielded an exact
   offline ground-truth signal that now lets us evaluate stage prediction without
   spending simulation time.
