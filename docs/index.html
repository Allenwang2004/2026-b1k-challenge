Counting What’s DoneGrounding Task Progress in Symbolic Goals for Long-Horizon VLA Policies

A vision-language-action policy that tracks progress by counting satisfied BDDL goal literals instead of guessing how far into the episode it is.

Code (soon) Report (soon) Challenge

TL;DR

The 2025 winning solution conditions its action expert on a task stage: an integer saying which phase of the task the robot is in. That integer was defined as a fixed fraction of the episode's total length. At test time the episode length is unknown, so the policy was trained to predict a target it can never observe.

We redefine the stage as the number of BDDL goal literals currently satisfied. This is a function of the world state, so it is defined at every instant, both in training and at deployment. It is also exactly what the benchmark scores. On picking_up_trash the retrained policy reaches q = 0.733 with 4/10 successes.

On long-horizon tasks the stage predictor still fails, and we can say why. The demonstrations never contain a moment where nothing is happening, so the model never learns to answer "no progress yet". Our next change, a two-frame event head, targets exactly that. This page reports what works, what does not, and what we are testing now.

The Challenge

A mobile bimanual robot must complete long household activities in the OmniGibson simulator, using only its cameras and its own joint readings.

The 2026 edition covers 100 activities from BEHAVIOR-1K. Each activity is defined in BDDL, a symbolic language. The goal is a conjunction of literals such as inside(carrot_1, bowl_1) or not open(cabinet_1). An episode is scored by q-score, the fraction of goal literals satisfied when it ends. It counts as a success only if all of them are satisfied.

  • Long horizon. Episodes run for up to several minutes of simulated time. sorting_vegetables has a 10-minute cap and 13 goal literals.
  • Non-Markovian. Two moments can look alike to the cameras but call for different actions: before the first item is placed and after the last, the scene can look much the same. The policy needs some notion of progress.
  • Mobile and bimanual. Navigation, two-arm manipulation and articulated objects all appear within a single episode.
  • Expensive evaluation. At our measured ~0.2 s per simulator step, one pass over all 100 tasks × 10 public instances is on the order of 900 GPU-hours.

Method

Starting point

We build on the winning 2025 solution (Larchenko et al., arXiv:2512.06951). It is a Pi0.5 VLA (SigLIP vision encoder with a Gemma backbone) that replaces the text prompt with learned task embeddings. Its "System 2" predicts the current task stage, and the predictions pass through a voting tracker. The tracked stage is embedded and fed back to the action expert. We start from the released checkpoints, port the data pipeline to the 2026 demonstrations, and change only what the stage means.

The problem: a stage that cannot be computed at test time

In the original solution the stage label for demonstration frame t is:

stage = floor(num_stages × t / episode_length)

This requires episode_length, the total length of the episode. It exists only in the offline dataset, after the fact. During a rollout it is undefined. The head is supervised on elapsed-time fractions, but it is asked to report progress in a world where "elapsed fraction" has no referent. Whatever it learns, it is not the quantity it was trained on.

Our fix: count satisfied goal literals

stage = number of BDDL goal literals satisfied in the current state

The simulator already evaluates these literals, because that is how the benchmark scores an episode. We replay every demonstration, evaluate the goal every 30 simulator steps, and store the count as a per-frame label. The stage now changes when something actually happens, not when a clock ticks over.

Time-split stage

Same label for "walking to the bin" and "dropping the item" whenever they fall in the same time slice.

BDDL stage

A function of the observable world state → defined at every instant, in training and at inference alike.

Measures the same thing the benchmark scores.

A free, exact evaluation signal

The q-score is the fraction of satisfied literals, so for a task with N goal literals, q_score × N gives the stage an episode ended in, exactly, as an integer. Every rollout we have ever run is therefore labelled ground truth for the stage predictor. We can measure stage-prediction changes offline from logged rollouts without spending simulation time. The analysis below uses this signal.

Terminal-stage clamp

The evaluator ends an episode as soon as every literal holds. So while an episode is still running, a reading of the terminal stage can only be a false positive. Acting on it tells the policy it is done, and it stops. We never condition the action expert on the terminal stage: the tracked stage is clamped to N−1 for tasks with three or more stages.

The voting tracker promotes on 2 of 3 votes and can skip two stages at once. It demotes only on 3 of 3 votes, and only by one stage. A rapidly fluctuating input therefore ratchets upward. When the tracker reports stage 12 while the true stage is 4, the action expert is told that twelve items are already sorted. It then executes behaviour unrelated to the scene in front of it.

Root cause: "nothing has happened" is never in the training data

Across all 200 demonstrations per task, the BDDL stage sequence is essentially monotone, and every demonstration runs to completion. In the training distribution the stage always advances, so any feature that correlates with elapsed time scores well. That explains the 0.986 training accuracy.

A rollout that stalls for minutes in an unfamiliar scene is out of distribution. The model has no "no progress" answer to give. It picks confidently among fourteen options, and the tracker accumulates the noise.

Next: a Two-Frame Event Head in progress

We change the question so that "no, nothing happened" becomes the overwhelmingly common answer, and give the model the evidence it needs to answer it.

1. Two points in time

BDDL labels are sampled every 30 steps and held, so a label changes 0–1 s after the event that caused it. By then the labelled frame shows a finished state, not a transition, and a transition cannot be seen in a single frame. We therefore add the three camera views from 40 frames earlier (1.33 s, exactly two inference intervals) alongside the current three.

  • No extra inference cost. The policy is already queried every 20 steps, so the frame at t−40 is the observation from two calls ago. We cache it, and the simulator interface is unchanged.
  • Pretrained layout preserved. History views are appended after the current views, so the original three cameras keep their token positions.
  • Fits in memory. 74.9 GiB → 80.6 GiB per GPU during training.

2. A binary question

"Did a BDDL goal literal change during the last 1.33 s?"

Across the same 200 demonstrations, 96% of the answers are "no". The model is now trained, on the vast majority of its examples, to say that nothing has happened. That is precisely the response the 14-way head cannot give. The question also cannot be answered from one frame, so the second time point becomes necessary rather than merely available.

3. Stage by counting

Labels are monotone and each transition is +1, so the stage is recovered by counting detected events:

stage = number of detected events so far
  - count only rising edges   (overlapping 40-frame windows fire twice per event)
  - refractory period after each event (10–15 queries)

A real stage lasts 861 frames on average (43 queries), so the refractory period misses nothing real. Unlike the voting tracker, this has a hard ceiling on how fast the count can climb.

4. Keep the old head, compare both

The 14-way head is retained and trained (30,735 parameters, 0.0009% of the model) but no longer drives conditioning. Logging both heads during a rollout and comparing them against q_score × N answers directly which formulation is better. The bar is concrete: the event head must beat the constant baseline (MAE < 2.00), which the current head does not.

Caveats

What these numbers can and cannot support, stated plainly.

Evaluation is substantially non-deterministic

We ran the same checkpoint on the same instances twice:

InstanceRun 1Run 2Difference
301q = 0.692 (stage 9/13)q = 0.385 (stage 5/13)−0.308
302q = 0.231 (stage 3/13)q = 0.000 (stage 0/13)−0.231

Single-instance spread is larger than most model differences we have tried to measure. A likely contributor is that the policy's random number generator is not reset between episodes. The outcome of an episode then depends on how many episodes ran before it. Until that is fixed, no single-run A/B at n = 10 should be read as conclusive.

No clean baseline comparison yet

For the unmodified 2025 checkpoint on these tasks we have only partial runs. On the instances where both exist, the models are indistinguishable. On picking_up_trash (instances 301–302) the BDDL model and the 2025 checkpoint both average 0.833 (1.000 with the clamp, on n = 2). On sorting_vegetables (6 instances so far) both average 0.333. The per-instance chart above shows these side by side. The case for the BDDL stage rests on correctness, since the old target is not computable at inference. It does not rest on a measured improvement over the baseline.

Single tasks, not the benchmark

All results so far are on two of the 100 tasks. They do not predict the full-benchmark score.

Summary

  • Ground the stage signal in the task definition. Counting satisfied BDDL literals replaces a target that cannot be computed at test time with one that is always defined, and it aligns what the model tracks with what the benchmark scores.
  • q-score is free ground truth for stage prediction. Every past rollout becomes a labelled evaluation for the stage tracker, so we can iterate without new simulation.
  • Training accuracy hides the real failure. Demonstrations always make progress, so the model never learns "no progress". A binary, two-frame event objective puts that answer in 96% of training examples. We are testing it now.
